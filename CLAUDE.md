# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Chrome extension (Manifest V3, vanilla JS, no build step, no dependencies) that auto-follows and comments on Threads (threads.com / threads.net) posts that invite "mutualan" (mutual follow). The UI text, logs and code comments are in Bahasa Indonesia; keep them that way.

## Files
- `manifest.json` – MV3 manifest. Content scripts: `defaults.js` then `content.js` on threads.com/net at `document_idle`. Only permission is `storage`. There is **no background/service worker** – popup and content script talk directly.
- `defaults.js` – `THREADS_BOT_DEFAULTS` (keywords, comment templates, delays, limits, flags). Shared global, loaded by both popup and content script.
- `content.js` – the bot. Runs in the Threads page.
- `popup.html` / `popup.js` / `popup.css` – settings form, Start/Stop, stats, last 20 log lines.
- `icons/` – generated PNGs (16/48/128).

## How it works
- Popup saves the form to `chrome.storage.local.settings`, then sends `{type:'start'}` to the active tab. Other messages are `stop` and `ping` (which returns `{running}`). Because there is no background worker, a tab loaded before the last extension reload has no content script and every message fails with "Bot belum aktif di tab ini" – the fix is always to refresh the Threads tab.
- `content.js` `start()` only checks that the user is logged in. It works from any Threads page, because the first `cleanUp()` in `run()` navigates to Beranda (`location.pathname === '/'`). The `run()` loop:
  `cleanUp` → scan post cards → skip seen/processed/own posts → keyword match → skip if `alreadyFollowing` → `markProcessed` → `doFollow` → `cleanUp` → `findCard` (re-locate by post ID) → `doComment` → `cleanUp` → random delay → repeat.
- **A post we can't follow from is skipped entirely – no comment.** `skipReason(card)` has one rule: a visible `RE.follow` button must be present, otherwise skip. Field logs showed Threads renders **no button at all** on a feed card for an account you already follow – it does *not* become "Mengikuti" – so "no button" is the common already-followed case, not an edge case. `alreadyFollowing(card)` (a visible `RE.followed`) only distinguishes the two for the log message. Both roots **must** be the card – Beranda has a "Following" feed tab that would otherwise match at document level.
  Checked in two places. The scan loop is primary: it `continue`s to the next card in the same pass, so no extra scroll is needed, and it deliberately does **not** `markProcessed` – a skip is not an action, so it shouldn't consume the 2000-entry history or lose the post forever if `RE.follow` ever breaks (`seen` already prevents rechecking during this page load). `doFollow()` re-checks and returns `'skip'` as a second line of defence, because the card can change between the scan and the action; `run()` then sets `skipComment`. Skips count toward `stats.skipped`, never toward `maxActions`.
  The trade-off is deliberate: if `RE.follow` ever stops matching, the bot skips everything and does nothing, rather than commenting on everyone. `run()` counts those skips in `noFollowSkips` and names them in the idle stop reason, because a bare "Tidak ada postingan mutualan baru" would hide exactly that failure.
- `markProcessed` runs **before** the follow/comment attempt, so a mid-action page reload cannot make the bot act on the same post twice. A failed action is therefore not retried – that is intentional.
- `cleanUp()` = `dismissPopups()` and then `goHome()` if the page left Beranda. `goHome` tries the Beranda nav link, then `history.back()`, and as a last resort a hard reload to `/` with `storage.resume` set. The IIFE at the bottom of `content.js` auto-restarts from `resume` (carrying `stats` and the existing log lines over).
- Post cards can go stale after navigation, so always re-find a card with `findCard(postId)` instead of reusing an old reference.
- State flows one way: the content script writes `botState` (`running`, `reason`, `stats`, `logs`) to storage, and the popup renders it via `storage.onChanged`. Stats keys are `processed`, `followed`, `commented`, `skipped`, `unfollowed`.
- Liveness has two independent signals, because they answer different questions. `ping` proves the content script **exists**; the `heartbeat` storage key proves the loop is **making progress**. `beat()` writes it from inside `sleep()`'s loop (throttled to once per ~20 s) since that's what keeps ticking even during a 90 s delay, and the popup polls it on a 5 s interval and warns after 3 minutes of silence. Chrome can discard a background tab outright, which kills the content script while leaving `botState.running === true` in storage – without the heartbeat the popup would claim "Berjalan..." forever. It's a separate storage key on purpose: inside `botState` it would fight `saveState()` writes and re-render the popup constantly.
- On load, the IIFE at the bottom also reconciles a stale `botState.running === true` with no `resume` present – that combination means the previous session died with its page (discarded tab, or a manual reload). The legitimate reload path from `goHome()` always writes `resume`, so it is unaffected.
- `processed` (post IDs, capped at 2000) persists across sessions. `seen` exists only for the current page load and is marked on *every* card scanned, so the loop never re-parses a card it already rejected.
- Keyword matching goes through `normalize()`: lowercase, every non-alphanumeric run collapsed to a space, wrapped in spaces. A keyword matches at a word start only (`n.includes(' ' + kn)`), so `fb an` matches "fb-an" but `mutual` does not match "semutual".
- When the feed runs dry (`MAX_IDLE_SCROLLS` idle scrolls), the bot does not stop. `refreshForNewPosts()` waits `REFRESH_WAIT_MIN`–`MAX` seconds, writes `resume` (with `emptyRefreshes`), and reloads `/`. The resume IIFE then continues the session. `emptyRefreshes` resets as soon as a target is found, and the session stops after `MAX_EMPTY_REFRESHES` consecutive empty refreshes.
- Safety stops: `maxActions` reached, `MAX_EMPTY_REFRESHES` consecutive empty refreshes, a limit dialog (`RE.limited`, re-checked after each follow and comment), or a blocking popup that refuses to close.
- `cleanUp()` only runs *inside* the loop, so every exit path (limit, idle, manual Stop, error) could leave a popup on screen. `finalSweep()` covers that: it is chained in `start()` as `run().catch(...).then(finalSweep)` – deliberately **not** inside `stop()`, which is also called from the message listener and would race the in-flight action. Letting `run()` unwind first means one sweep covers every exit exactly once. It is skipped when `reloading` is set, because `goHome()`'s last-resort `location.assign('/')` clears popups anyway.

## Unfollow mode

- A second loop, `runUnfollow()`, selected by `start(null, 'unfollow')`. The popup sends `{type:'start', mode:'unfollow'}`; `ping` returns the active `mode` so the popup can label the status and disable the other mode's button. One loop at a time – `start()` still refuses when `running`.
- **`cleanUp()` must never be used in this mode.** It calls `goHome()` whenever `location.pathname !== '/'`, which would drag the bot off the Following list on every iteration. Use `dismissPopups()` alone. This is the easiest thing to get wrong here.
- Flow: `openList('followers')` → `scrapeList()` → `openList('following')` → `scrapeList()` → `unfollowTargets()` → unfollow one by one with the shared `delayMin`/`delayMax`. The delays are deliberately shared with follow mode: unfollowing is rate-limited by Meta just as much.
- `scrapeList()` accumulates usernames into a `Set` **as it scrolls**. Threads' lists are virtualised – rows are removed from the DOM as you scroll past – so reading the DOM once at the end would only capture the last chunk. It scrolls the list's own scroll container (`scrollContainer()` walks up for `scrollHeight > clientHeight`) rather than the window, because the list usually lives in its own scrollable panel.
- `openList()` clicks its way there via `RE.profileNav` → `RE.followersNav`/`RE.followingNav` instead of building a URL, so a change in Threads' URL shape doesn't break it.
- **`RE.followingNav` and `RE.followed` both match "Mengikuti" and must stay separate.** One is a navigation link on the profile page, the other is the button in a list row. Merging them would make the unfollow button search grab the nav link instead.
- `findRow(username)` is re-resolved for every single unfollow, never cached: the list reflows each time an account is removed, so a stored row goes stale – the same reason `findCard(postId)` exists for the feed.
- Unfollow confirmation is checked **inside the row** (`RE.follow` reappearing, or the row disappearing). A document-wide check is meaningless here: the list is full of other people's Mengikuti buttons.
- `unfollowTargets(following, followers, followed, settings)` is pure and therefore the part worth unit-testing. Rules: skip if they follow back, skip if whitelisted, skip if we followed them less than `unfollowAfterDays` ago. **A username with no `followed` timestamp is treated as past the grace period** – it was followed manually, or before this feature existed. That is what makes the first run able to touch manually-followed accounts, so the whitelist is the only guard; `maxUnfollows` defaults to a deliberately low 10 and the target list is logged *before* anything is clicked.
- Storage key `followed` is `{username: timestamp}`, written by `markFollowed()` only once a follow is *confirmed*, and trimmed to the 2000 most recent.

## DOM conventions (most fragile part)
- Threads class names are obfuscated, so **never select by class**. Use `data-pressable-container`, `aria-label`, `role`, `href` patterns and visible text.
- All selectors live in `SEL`, and all label regexes (English + Indonesian) live in `RE` at the top of `content.js`. Change them there, not inline.
- `findClickable(root, regex)` matches in this order: `aria-label`, then `<svg><title>`, then element text – and returns the nearest `SEL.clickable` ancestor. Reuse it instead of writing new queries.
- `getPosts()` drops nested cards (quoted/embedded posts) by rejecting any card whose parent chain contains another card. `parsePost()` gets the post ID and author from the `/@user/post/ID` link, so a card without one is skipped.
- Text is typed into the composer with `document.execCommand('insertText')` so the React editor registers the input. Setting `textContent`/`value` will not work. That goes through `typeInto(editor, text)`, which **verifies the text actually landed** and falls back to a synthetic `beforeinput` (Threads' Lexical editor reads `event.data`) before giving up. `execCommand` depends on document focus and can fail silently in an unfocused tab, so never click send without that confirmation – an unverified insert means an empty or half-written comment gets posted.
- `waitFor(fn, timeout)` is driven by a `MutationObserver` on `document.documentElement`, not by polling. Observer callbacks arrive as microtasks after a DOM change, so the *success* path doesn't depend on timers at all – that's what keeps it working in a hidden tab, where a 250 ms poll would get only one shot. A `delay(250)` poll is still raced alongside it for conditions that aren't DOM mutations (notably `waitFor(isHome, …)`, which reads `location.pathname`). The wake signal is **re-armed on every iteration**: an already-resolved promise wins every subsequent race, which would spin the loop at full speed until the timeout.
- Clicks go through `realClick()` (full pointer/mouse event sequence, with `scrollIntoView`). The one deliberate exception is the comment send button: it uses a plain `.click()` so the scroll does not shift the dialog out from under the click.
- Comment send button: `findSendButton(editor, replyBtn)` searches only inside `composerScope()`. That scope is the dialog, or for an inline composer the largest ancestor of the editor that does not yet contain the card's action bar (`replyBtn`). Within it, a button with matching text (`RE.post`) wins first, then an icon whose label matches `RE.post` and does not match `RE.share`. Never add "bagikan" to `RE.post`: the Indonesian Share icon is labelled "Bagikan". The fallback is Ctrl+Enter, and the log then lists the composer's buttons (`describeComposer`) so the right label can be added to `RE.post`.
- Comment success is inferred, not confirmed: the editor disappearing, going invisible, or going empty within 15 s counts as sent. On failure `closeComposer()` dismisses the composer and answers the "Buang" prompt.
- Reply button fallback: `findReplyByPosition(card)` finds the Like button and takes the next icon button in the same action row (like → reply → repost → share). Used when `RE.reply` matches nothing; `describeButtons(card)` is logged so the real label can be added to `RE.reply`.
- After following, Threads often leaves a profile hover card open, and that card blocks the comment step. It is not always `role="dialog"`. `findProfileCards()` detects it as a Follow/Mengikuti button outside any post card (and outside `nav`/`header`) that has a `fixed`/`absolute` ancestor, and `openPopups()` includes it. `closeProfilePopup()` sends pointer/mouse-leave to the Follow button, presses Escape, and clicks an empty spot.
- `openPopups()` is the single detector for "something is covering the page": `role="dialog"|"menu"|"tooltip"|"alert"`, `aria-modal="true"`, floating profile cards, and **a visible composer that still has text in it**. An *empty* composer must never count – the always-present compose box on Beranda would make `dismissPopups()` loop and log a false warning every cycle, so only text (which can only come from our own `doComment()`) qualifies. Nested matches are deduped so counts and logs don't inflate.
- `clickEmptySpot()` escalates through three stages and returns the name of the one it used (`'luar'`/`'overlay'`/`'document'`, or `null`) – a truthy string, so callers that treat it as a boolean still work.
  1. `clickOutsideSpot()` – a point genuinely outside every open popup. Do **not** reinstate the old `isFloatingCard(el)` check here: that helper returns any `fixed`/`absolute` ancestor, and Threads' own header/sidebar are positioned, so every candidate point could be rejected and dismissal would fail silently. `isFloatingCard()` is still correct inside `findProfileCards()`, where the Follow-button filter gives it meaning.
  2. `clickOverlaySpot()` – a popup that covers the whole viewport leaves no "outside" at all, so stage 1 *cannot* succeed. The way out is to click the overlay itself in the empty area outside `contentRect(popup)` (the largest visible descendant under 80% of the viewport, i.e. the actual card). Kept for genuine full-screen modals, but note the stuck profile card was **not** one: field logs show `klik: luar` on a `25%x32%` popup, so stage 1 fired correctly and the card still refused to close. Clicking outside is not what dismisses it – don't assume this stage is the fix for a lingering card.
  3. `clickDocument()` – dispatches on `document.documentElement` so `e.target` is outside the card by construction, which fires plain `document.addEventListener('mousedown', …)` handlers. **React's listeners sit on the root container, and events dispatched on `documentElement` (an ancestor of it) never reach them** – this only helps non-React handlers, which is why it is last. Don't promote it expecting more.
- `forceHide(el)` is the last resort when every gesture fails: `style.display = 'none'`, chosen over `remove()` so it stays reversible and doesn't break the structure React holds. It only ever hides an element the app itself marked a popup (`POPUP_ROLES`), descending into one if the node it was handed isn't marked – `findProfileCards()` can return a positioned ancestor that is a *shared portal container*, and hiding that would make a later composer invisible, breaking every comment until a refresh. Three further guards, all required: not `isBlockingPopup` (never force a composer or confirm dialog – hiding one without cancelling its state confuses Threads afterwards), no `SEL.postCard` inside it (that would be the feed, since `findProfileCards()` can return a large positioned ancestor), and smaller than 60% of the viewport. Once hidden, `visible()` goes false so `openPopups()` stops reporting it.
- `scrollNudge()` (1px down and back, instant) is an early rung in both `dismissPopups()` and `closeProfilePopup()` – hover cards and popovers usually dismiss on scroll, and it's the cheapest gesture available.
- `describePopup()` reports size as a percentage of the viewport. A popup logged as `100%x100%` is a full-screen overlay, which is the direct explanation for stage 1 failing.
- `dismissPopups(wait = sleep, force = false)` escalates per attempt (max `TRIES_DISMISS`): Escape → `clickEmptySpot()` → `RE.discard` confirm → on the **last** attempt only, a close button found by `findClickable(popup, RE.close)` inside that popup. Never guess a close button by position: a profile hover card has none, and clicking an arbitrary button there navigates to someone's profile. Candidates matching `RE.post`/`RE.share` are rejected so Kirim/Bagikan can never be clicked as "close".
- It returns a boolean and logs survivors with `describePopup()` (role + labels + text snippet) so the real label can be added to `RE.close`/`RE.discard`. Survivors go into the `stuck` WeakSet and are reported once – they stay in `openPopups()` (so `clickEmptySpot()` keeps avoiding them) but are no longer fought every cycle. `force = true` ignores `stuck`, used only by the final sweep.
- **`role="dialog"` alone does not mean "modal".** Threads renders the profile preview card as a `role="dialog"` with no close button, no `aria-modal`, and no `aria-label` anywhere inside – seen in the wild as `dialog 25%x32% "L,arcelia … 188 pengikut Mengikuti"`. It doesn't block the next click, so treating it as blocking kills the session for nothing.
- `blockingReason(el)` returns *why* a popup blocks, or `null`. Order is deliberate and load-bearing:
  1. a composer inside (`SEL.editor`) always blocks, checked **first** because the post-detail dialog has a composer *and* a follow button, and there the composer is what matters;
  2. **a positive profile-card signal** – a visible `RE.follow`/`RE.followed` button with no composer – means never blocking;
  3. only then `aria-modal`, `role="menu"`, and a `role="dialog"` carrying `RE.close`/`RE.discard`/`RE.post`.
  Step 2 exists because the earlier "require evidence of a modal" approach, which reasoned from the *absence* of close buttons, still misjudged a real card in the field – and that single misjudgement both stopped the session and made `forceHide()` refuse to hide it, since both hang off this one predicate. Reason for an *inclusion* beats reason from absence; don't reorder these.
- `isBlockingPopup` is just `!!blockingReason(el)`. The reason string gets logged, because a misjudgement here is otherwise undiagnosable – it already cost two wrong stops.
- Stopping the session is the most expensive reaction available, so `cleanUp()` requires `MAX_BLOCKED_CLEANUPS` (3) *consecutive* blocked cleanups first, and the counter resets on any clean one. `doComment()` already handles a blocked composer gracefully, so continuing beats dying. The stop is also gated on `running`, so a manual Stop is never relabelled with a popup reason.
- `closeProfilePopup(followBtn, card)` sends leave events to the card's profile links as well as the Follow button: the hover trigger is normally the avatar or username link, so a `mouseleave` aimed only at the Follow button never closes it.
- `pressEscape()` fires both `keydown` and `keyup`, and targets every open popup in addition to `activeElement`/`document` – some Threads handlers sit on the popup element itself.
- When `dismissPopups()` gives up it logs which click stage was reached (`klik: luar/overlay/document/TIDAK ADA`) alongside each popup's size. Those two numbers are the first thing to check when a popup won't close, and both are invisible otherwise.
- The `visibilitychange` log is debounced by 3 s and only fires on a real state change. The log keeps 20 lines; a few tab switches used to evict everything useful.
- Follow confirmation must be checked inside the card or dialog only. Beranda has a "Following" feed tab that would give a false positive.

## Working on this repo
- No tests and no build. Check syntax with `node --check content.js popup.js defaults.js`.
- To test, go to `chrome://extensions`, reload the extension, **refresh the Threads tab**, then use **Dry run**, then **Maks aksi = 1**.
- Use `sleep()` (interruptible, checks `running`) for any wait inside the loop, so Stop responds quickly. `step()` is the standard 1–3 s human-ish pause between clicks; `waitFor(fn, timeout)` polls for a DOM condition and is *not* interruptible.
- `hold(ms)` is a non-interruptible wait and exists for exactly one reason: anything running *after* the bot stops. `sleep()` returns instantly once `running === false`, so post-stop cleanup done with `sleep()` would fire Escape and clicks with no gap for the DOM to react. Only `finalSweep()` should need it – keep using `sleep()` everywhere inside the loop.
- **Never use a bare `setTimeout` for a repeated wait – always go through `delay(ms)`.** Chrome throttles timers in a hidden tab to ~1 s, and after the tab has been hidden 5 minutes to ~1 per *minute*. That 1/minute penalty only hits *chained* timers (a `setTimeout` scheduled from inside a timer callback raises the "nesting level"), so `delay()` bounces through a `MessageChannel` first to reset the nesting level back to 0. `sleep()`, `hold()` and `waitFor()` are all built on it. A bare `setTimeout` in a loop silently reintroduces the 1-minute stall.
- The bot is expected to keep working while its tab is hidden, so **anything that depends on rendering is off-limits in the loop**: animation frames, `IntersectionObserver`, and smooth scrolling do not run for a hidden page. Scroll calls take their behavior from `scrollBehavior()` (smooth when visible, instant when hidden) – don't hardcode `behavior: 'smooth'` again.
- Known limitation that cannot be fixed from the extension: Threads paginates the feed with its own `IntersectionObserver`, so **a hidden tab stops loading new posts**. `run()` therefore does not spend the `idleScrolls` budget while `document.hidden` – it logs once and waits, because "no new posts" is a wrong conclusion in that state. Don't "simplify" that branch away.
- Keep the bot slow and human-like. Do not lower the default delays or raise the default limits. `popup.js` `readForm()` also floors the delay at 5 s and `maxActions` at 1 – keep those guards.
- Adding a setting means touching four places: `defaults.js`, the `popup.html` form, `fillForm`/`readForm` in `popup.js`, and the reader in `content.js`.
- When behaviour or settings change, update `README.md` (Indonesian, user-facing), including its settings table.
